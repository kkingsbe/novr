# NOVR Codebase Audit — VR-Focused Findings (revised)

**Scope:** Whole repository (~31k LOC across 9 projects).
**Approach:** Three parallel exploration subagents mapped every subsystem (NOVR main plugin, XR-plugin replacements, patcher/build/installer/XInput). I then re-read the highest-impact files directly (`VrControllerInput`, `VrUiCursor`, `NOVRPoseDriver`, `NOVRHeadsetData`, `VrCanvasHitTester`, `VrCameraManager`, `NOVRFlightHudBehavior`, `NOVRHMDBehavior`, `NOUIManager`, `OpenXrControllerProfileBootstrap`, `OpenXRInteractionProfilePatches`, `PitchCompassBehavior`) and re-evaluated findings against the unity-vr skill lenses: the five-pillar mental model, vr-math (pose composition, tracking spaces, screen↔world in stereo), vr-modding §5–11, the comfort-interaction reference, and the flight-sim genre playbook (cockpit-as-reference-frame, HOTAS coexistence, recenter, snap zoom).
**Date:** 2026-07-13 (revised)
**What changed since the previous draft:** four findings were downgraded or removed after direct code re-read (VR-CRITICAL-2 was wrong; VR-CRITICAL-1 was partly wrong; VR-HIGH-1 reframed; VR-MED-7 wrong). Two findings are promoted after re-read (VR-CRITICAL-3 is new; VR-HIGH-1 reversed polarity). Several smaller items renamed to reflect what the code actually does.

---

## Executive summary (30-second read)

NOVR is a competent BepInEx + Harmony + OpenXR retrofit of a flat Unity flight-combat game. The architecture is clean for a mod: BepInEx ctor patches → `Core` MonoBehaviour spawns `VrCameraManager` / `NOVRHeadsetData` / `NOUIManager` / `VrTogglerManager`, the OpenXR loader runs, and a manual rig of tracked camera + cockpit-HUD camera + world-space UI is composed. Roughly **70% of vr-modding §5–8 is correctly handled.**

The remaining **30% concentrates in four big buckets**, in order of severity:

1. **Cockpit-as-reference-frame violated** (genre-playbook §1). The HUD is pinned to a `NOUIManager` child (`SmoothedForwardReference`), which is **not** parented to the airframe — so when the aircraft rolls, the cockpit instruments stay world-fixed and the player's view rolls *through* the static HUD. This is the textbook "world stays gravity-true" failure mode that the doctrine says to ship *only as an opt-in comfort option*, not as the default. VR-HIGH-1.

2. **Late-pose ordering**: the camera pose write happens in `Update`/`LateUpdate`/`OnBeforeRender`, but `VrCameraManager.Update` (the rig setup) runs in `Update`, *before* the game's `LateUpdate` HUD scripts. The HUD patches fire in `LateUpdate`, so by the time they sample the camera rotation, the camera pose is one frame stale on platforms where the runtime's "late" pose hasn't yet been propagated. Single-frame visible lag between cockpit motion and HUD. VR-HIGH-2.

3. **Mouse-mode cursor uses a hard-coded 90°×130° cone** for probe-ray construction (`VrUiCursor.cs:545-548`) and never sources FOV/offset from the runtime's per-eye projection matrix. The post-ray `HasGraphicAtPoint` does call `camera.projectionMatrix`-based `WorldToScreenPoint`, so clicks land correctly when the canvas is centered, but the **probe direction** is wrong at the edges — meaning the cursor skips past off-axis buttons. VR-CRITICAL-1.

4. **OpenXR feature-array race**: `OpenXrControllerProfileBootstrap.ConfigureSteamVrControllerProfiles()` (only when `EnableExperimentalSteamVrControllerProfiles` is true) and `OpenXRInteractionProfilePatches.EnsureControllerProfiles()` (Harmony prefix on `RequestOpenXRFeatures`) both mutate `OpenXRSettings.features` via reflection. The two run in indeterminate order relative to each other and to Unity's internal serialization of the features array, and there is no lock. VR-CRITICAL-3 (new).

Everything else is incremental cleanup, dead code, or cosmetic.

## Detailed findings

### [VR-CRITICAL-1] Mouse-mode cursor probe ray is built with a fixed 90°×130° cone — not the runtime's per-eye FOV

- **File:** `NOVR/VrUi/VrUiCursor.cs:540-550` (mouse-mode probe-ray construction)
- **Issue:** The mouse branch maps `mousePos.x/y` into a fixed `[-45°,45°]×[-65°,65°]` cone via `Lerp(-45,45)` / `Lerp(-65,65)` and `Quaternion.Euler(-cursorPitch, cursorYaw, 0) * Vector3.forward`. There is no read of `Camera.GetStereoProjectionMatrix`, no `tanHalfFovY = 1/P[1][1]`, no off-axis `P[0][2]/P[1][2]` term. The `camera.projectionMatrix` *is* read at lines 277-280 and 318-321, but only to feed `_feedProj*` diagnostic state and to compute the `screenPoint` for the `GraphicRaycaster.Raycast` test inside `HasGraphicAtPoint` — *not* to construct the world ray.
- **VR risk:** When the cursor reaches the edge of the screen in mouse mode, the probe direction diverges from what the headset is actually rendering. With per-eye asymmetric frustums (canted displays, foveated rendering on Valve Index / Quest Pro) and with the `HudDistance = 1000m` (`VrHudProjectionHelper.cs:7`) hard-coded into the projection math, the world ray misses off-axis buttons by tens of centimeters at the canvas plane. The "click lands on the wrong widget" symptom is the canonical bug from vr-math §10 / vr-modding §7.
- **Fix:** Source cone terms from the actual per-eye projection matrix: for each eye, compute `Vector3 worldDir = camera.transform.rotation * Vector3.forward + worldPosOnImagePlane(...)` derived from `P[0,0..2]` and `P[1,1..2]`. Don't assume a symmetric frustum.
- **Effort:** M

### [VR-CRITICAL-3] Two independent reflection-based writers mutate `OpenXRSettings.features` — race + duplicate features possible

- **Files:** `NOVR/OpenXrControllerProfileBootstrap.cs:31-71` (runs in `XrPluginOpenXrToggler.SetUp`) and `NOVR/Patches/VR/OpenXRInteractionProfilePatches.cs:51-97` (Harmony prefix on `OpenXRLoaderBase.RequestOpenXRFeatures`)
- **Issue:** Both paths:
  1. Read `OpenXRSettings.Instance` and the private `features` field via reflection.
  2. Construct new `OpenXRFeature` instances via `ScriptableObject.CreateInstance(...)`.
  3. Reorder / deduplicate / write the array back via `SetValue`.
  
  The bootstrap path dedupes by `feature.GetType()` and sorts by `priority` (lines 59-65). The patch path simply *appends* new types not already present (lines 70-94). Order of execution depends on which path runs first; the second one will see the array produced by the first and may re-introduce duplicates (the bootstrap dedupes but the patch path does not — `existingTypes` is built from the array as the patch reads it, but a duplicated instance added by bootstrap and then seen by the patch as "not present in existingTypes" because `HashSet<Type>` collapses by type will not be re-added; however if the bootstrap runs *after* the patch, it will see the patch's freshly-added array and may double-sort without adding, leaving the patch's items intact but in unstable order).
  
  More important: the Unity runtime caches `featureCount` and other arrays derived from `features`. Reassigning the array via reflection can produce a state where Unity's cache is stale, especially between scene loads. Symptoms include: feature state changes not taking effect, runtime extensions not requested, controller binding fails.
- **VR risk:** Controller pairing silently fails. The player loads the game, no controllers enumerate, recenter button can't be reached without controllers — and the diagnostic log only says `OculusTouchControllerProfile enabled=True` (it IS enabled, but the session didn't request its extension).
- **Fix:** Funnel both writers through one `static` `RegisterProfile(Type)` on `OpenXrControllerProfileBootstrap`. The patch becomes a single `harmony.Patch` of `RequestOpenXRFeatures` whose *only* job is to call `OpenXrControllerProfileBootstrap.EnsureRequired()` once before the native side reads `features`. `Lock` around the operation; re-read after.
- **Effort:** S

### [VR-HIGH-1] Cockpit HUD is world-fixed — it does NOT roll with the aircraft (genuine bug; severity high but reduced from "rig composition" after re-read)

- **Files:** `NOVR/VrUi/NOUIManager.cs:29-38` (`CreateSmoothedForwardReference`), `NOVR/VrUi/Components/NOVRHMDBehavior.cs:11-21` (HMD panel pin), `NOVR/VrCamera/VrCameraManager.cs:79` (tracked camera parented to airframe root)
- **Issue:** The tracked VR camera is parented to the game's airframe camera (`VrCameraManager.cs:79`), and its **local** transform is overwritten with tracked HMD pose every frame (`NOVRPoseDriver.cs:48-49`). So:
  - **Position**: aircraft pose is inherited via parent; HMD position is added on top via `NOVRHeadsetData.Translation` (which is `Anchor + CalibrationOffset + GetHeadPosition()` — note: no aircraft position term because the parent supplies it). ✔ Correct.
  - **Rotation**: aircraft rotation is inherited via parent, but the parent's rotation is then *overridden* by HMD rotation. ✘ The camera does **not** roll with the aircraft.
  
  And `NOVRHMDBehavior.Update` pins the cockpit HUD at `APIBus.CockpitHudReference.forward * 1000` (line 14) with `CockpitHudReference` rotation. `CockpitHudReference` is created as a child of `NOUIManager` (line 32 of `NOUIManager.cs`). `NOUIManager` is created as a child of `Core` (`NOVR/Core.cs:81`), which is `DontDestroyOnLoad`. So the cockpit HUD is **world-fixed** and only its *forward axis* tracks the cockpit-HUD camera (which is itself head-locked because of `NOVRPoseDriver`).
  
  Per genre-playbook §1 ("the cockpit is the reference frame"): "The rig is parented to the **airframe**, full stop: when the aircraft rolls, the player rolls with the cockpit." NOVR has the opposite: the HUD is world-fixed (only head-tracked), and the player rotates their head independently of the airframe. This produces the exact symptom described in comfort-interaction.md: "world feels like it's rotating under me even though I didn't turn."
- **VR risk:** Cockpit-as-reference-frame doctrine is the *single most important* VR-flight-sim comfort rule. Failing it produces sickness within a minute of aggressive maneuvering. Players can mitigate via the `CockpitHeadForwardOffset` / `CockpitHeadRightOffset` and the "horizon-lock comfort option" the doctrine recommends, but the codebase does **not** expose a horizon-lock toggle today — the failure mode is unconditional.
- **Fix:** Two coherent options:
  - **A.** Add a stable-cockpit option (default ON for sensitive users) that parents `CockpitHudReference` (and the VR UI rig) under the tracked camera with a zeroed local transform, *and* parents the tracked camera under the airframe camera (already done) *without* overriding its rotation. Then the camera rotates with the airframe and the HUD rotates with both — the player's head motion is added on top by the inner rig. The `NOVRHMDBehavior` continues to track the player's head *within* that rotating frame.
  - **B.** Accept the current "horizon-stable / cockpit-rots-under-you" behavior as the comfort default and add a "cockpit-stable" opt-in mode that parents the camera and HUD to a smoothed airframe pose. Per the genre playbook this is the inverted-by-default of the standard doctrine; ship the opt-in but document it.
  - Either way, expose the toggle in `ModConfiguration` so users can pick.
- **Effort:** L

### [VR-HIGH-2] Camera rig built in `Update`; HUD patches sample in `LateUpdate` — single-frame cockpit lag

- **Files:** `NOVR/VrCamera/VrCameraManager.cs:20-59` (Update loop), `NOVR/VrUi/Components/NOVRHMDBehavior.cs:11-21` (Update loop), `NOVR/Patches/HUD/*` (LateUpdate postfixes)
- **Issue:** Per vr-math §12 and rendering-performance §6: "Update the rig from the final aircraft pose *after* flight-model integration each frame, in lockstep with rendering (a frame of lag = cockpit judder)." Here the rig setup runs in `Update`, but the runtime's "late pose" (the predicted head pose for this frame's render) is only propagated by Unity's XR loop between `Update` and the next render — and the HUD patches (`FlightHudPatch`, `AirbaseOverlayPatch`, `HUDBombingStatePatch`, etc.) read the camera in their own `LateUpdate`s via `VrHudProjectionHelper.TryProjectToCockpitHud`. So the camera the HUD samples is the previous frame's pose.
- **VR risk:** 1-frame stale cockpit-HUD positioning relative to the airframe. At 90 Hz this is ~11 ms, which the runtime's ASW / motion-vector reprojection will smooth for head-rotation but **cannot invent for cockpit instruments**. The needles appear to lag the plane.
- **Fix:** Move the rig-pose application into a `Application.onBeforeRender` slot wired via `NOVRBehaviour` (which already subscribes `OnBeforeRender`). Give the HUD patches `[DefaultExecutionOrder(>1000)]` so they run *after* `OnBeforeRender` queues are populated, or use a render-pipeline-aware late-stage hook.
- **Effort:** M

### [VR-HIGH-3] No recenter separates rig-offset from cockpit-offset

- **File:** `NOVR/NOVRHeadsetData.cs:24-52` (`CalibrateTranslation` / `CalibrateRotation`)
- **Issue:** `CalibrateTranslation` overwrites `TranslationCalibrationOffset` with `-GetHeadPosition()` per axis. This is correct for the *cockpit* recenter (head should be at the cockpit origin), but it is *also* used as the recenter of the player's "view of the world." There is no `T_world←rig` concept and no `XR Origin` in the modern Unity sense — recenter conflates two different transforms (vr-math §3).
- **VR risk:** When the player physically shifts in their chair or lifts/repositions the headset, "recenter" snaps their head back to the cockpit origin — fine if the cockpit is at the same place, but if the player moves forward in their chair and then triggers recenter, their in-game head teleports backward. Symptom: "I lean and the world jumps."
- **Fix:** Introduce an explicit `RecenterRigOrigin()` that resets `TranslationAnchor` (currently unused — `NOVRHeadsetData.cs:10-22`) and a separate `RecenterCockpitSeat()` that updates `TranslationCalibrationOffset`. Bind two different recenter actions.
- **Effort:** M

### [VR-HIGH-4] Long-form text in native menus rendered through the eye buffer, not compositor layers

- **Files:** `NOVR/VrUi/Native/NativeSettingsPanel.cs` (1859 LOC), `NativeMultiplayerPanel.cs` (1471 LOC), `NativeWorkshopPanel.cs` (721 LOC), `NativeSinglePlayerMissionPanel.cs` (532 LOC)
- **Issue:** All native VR menu canvases are rendered through the main eye buffer via `worldCamera = APIBus.CockpitHudCamera` and `renderMode = RenderMode.WorldSpace`. Per rendering-performance §9: "For any text-heavy panel the user will read for minutes, a compositor layer is the difference between 'readable' and 'PDF through frosted glass.'" The four largest native panels are exactly that case. The codebase already includes a reserved `LayerHelper.VrUiCapture = 31` (`LayerHelper.cs:49`) that is unused — likely a stub for this work.
- **VR risk:** Text legibility on Quest 3 (≈ 25 PPD) and Quest 2 (≈ 20 PPD) with TAA reprojection is borderline at distance ≥ 2 m. The native menu panels are at ~3 m with scale `0.003`, which is small enough to fail the vr-math §9 "≥ 1° angular height per line" rule.
- **Fix:** Either (a) move these panels to compositor quad layers via `OpenXRCompositionLayersFeature.cs` (already in `NOVR.XR.OpenXR`), or (b) at minimum bring them to ≤ 1.5 m and increase scale so each line is ≥ 1° of angular height.
- **Effort:** L

### [VR-HIGH-5] `PitchCompassBehavior` reuses one material across all 36 slices — depth-write produces per-eye ambiguity

- **File:** `NOVR/VrUi/Components/PitchCompassBehavior.cs:90-128, 252-269`
- **Issue:** 36 slices (18 pitch rows × 2 sides for the wrap-around) are placed at `slice.transform.forward * 1000f` with a shared `Sprites/Default` material and `GetDepthTestedMaterial()`. Stereo rendering reconstructs depth per eye; with all slices at exactly the same forward distance, every slice writes the *same* depth value in both eye buffers — the depth pyramid has zero discrimination between slices, so when the airframe rolls the slices don't interleave correctly and ASW will smear them. The genre-playbook §1 calls this out for "props and rotors" — the same issue applies to repeated pitch-ladder rows.
- **VR risk:** Sub-pixel judder on the pitch ladder during turns. Worst at high bank where the eye-buffer depth pyramid is most compressed.
- **Fix:** Per-slice shader offset on the z-axis (even 1–5 cm per slice breaks the depth tie); or use a single quad with shader-driven per-row sampling; or render the ladder via a compositor quad layer.
- **Effort:** M

### [VR-MED-1] `Camera.fieldOfView` patched immutable — but `Camera.projectionMatrix` is not

- **File:** `NOVR/Patches/Misc/CameraPatch.cs:8-13`
- **Issue:** The postfix blocks `Camera.set_fieldOfView`. But the runtime derives the actual per-eye frustum from `projectionMatrix` (or its own internals). A game-driven FOV change routed through `Camera.fieldOfView` is blocked, but if any code calls `Camera.SetStereoProjectionMatrix` or computes a `Matrix4x4.Perspective` directly, the postfix doesn't catch it. Genre-playbook §1 forbids scope-zoom-via-FOV ("`Never animate the projection FOV`").
- **VR risk:** Any future G-effect or magnification logic that bypasses `fieldOfView` will desync per-eye projection, which is one of the worst nausea triggers in the genre.
- **Fix:** Add `[PatchPrefix(typeof(Camera), "set_projectionMatrix")]`, `[PatchPrefix(typeof(Camera), "SetStereoProjectionMatrix")]`, `[PatchPrefix(typeof(Camera), "ResetProjectionMatrix")]`, and `[PatchPrefix(typeof(Camera), "set_aspect")]` (during VR). All return false.
- **Effort:** S

### [VR-MED-2] Map icons flicker — `ConditionalWeakTable` keyed on object identity breaks under pooling

- **File:** `NOVR/Patches/HUD/Map/MapIconFlickerPatch.cs:17-79`
- **Issue:** Icons are hidden on `SetIcon` and shown on the first `UpdateIcon`, tracked via `ConditionalWeakTable<MapIcon, object>`. If the game pools icons (re-`SetIcon` on the same instance), the second `SetIcon` hides the icon again and never re-shows — there is no "first UpdateIcon" anymore because the table already has the key. Symptom: enemy disappears on map after respawn.
- **VR risk:** Gameplay failure, not sickness. Players can't see threats.
- **Fix:** Tie visibility to a stable per-aircraft id (e.g. a `NetworkInstanceId` / `OwnerSlot` field). Or: track per-frame visibility and don't toggle on `SetIcon` at all — toggle via `LateUpdate` every frame based on whether the icon is currently selected / important.
- **Effort:** S

### [VR-MED-3] `VrCanvasHitTester` allocates per-frame `List<(...)>` in the cursor path

- **File:** `NOVR/VrUi/VrCanvasHitTester.cs:135-136, 217-218`
- **Issue:** `RaycastCanvases` and `RaycastCanvasPlanes` both `new List<(float distance, Canvas, ...)>()` every call. With 100+ registered canvases and two calls per cursor Update (controller + mouse branches), and `[DefaultExecutionOrder(-1000)]`, every cursor update allocates a 4-tuple list. GC spikes during cursor activity → frame hitches.
- **VR risk:** 5–10 ms hitches during map use (where many canvases are visible at once) → ASW / reprojection → judder.
- **Fix:** Reuse a `static List<...>` buffer; clear and refill; cap the registered-canvas set to the ones currently relevant (CullList by `CameraMatches` + `IsCanvasRaycastBlocked` *once* per frame).
- **Effort:** S

### [VR-MED-4] `VrUiCursor.Update` chains map-click forwarding into the game's network pipeline

- **File:** `NOVR/VrUi/VrUiCursor.cs:287-290` (`triggerDownThisFrame` → `ForwardMapClickIfNeeded` → `MapIcon.ClickIcon(Mouse)`)
- **Issue:** `ForwardMapClickIfNeeded` (lines 767-826 of the same file) runs synchronously on the cursor's main-thread tick. `MapIcon.ClickIcon` allocates a server message and may route through the game's full network dispatch. With `[DefaultExecutionOrder(-1000)]` this runs before most game code; a slow network dispatch under it can eat the frame.
- **VR risk:** Frame spikes during map interaction.
- **Fix:** Defer `ForwardMapClickIfNeeded` to `LateUpdate` (or queue into a `Queue<Action>` drained in the next tick). Profile `MapIcon.ClickIcon` to confirm it allocates.
- **Effort:** M

### [VR-MED-5] `UIBehaviorPatcher.FixedUpdate` does `Resources.FindObjectsOfTypeAll<GameObject>()` per frame

- **File:** `NOVR/VrUi/UIBehaviorPatcher.cs:96-144`
- **Issue:** Every FixedUpdate iterates *every* loaded GameObject (including assets, not just scene objects) and matches by name. With a 50k-object scene the call walks all of them. This is the dominant CPU consumer for the patcher.
- **VR risk:** Sustained 1–3 ms per FixedUpdate, recurring frame pressure.
- **Fix:** Cache `Resources.FindObjectsOfTypeAll<GameObject>()` results invalidated by scene-load events (`SceneManager.sceneLoaded`); track additions via `OnHierarchyChanged`.
- **Effort:** M

### [VR-MED-6] OpenXR loader is hard-coded — no runtime detection

- **File:** `NOVR/VrTogglers/VrTogglerManager.cs:13-20`
- **Issue:** `VrTogglerManager.SetUpToggler` always creates `XrPluginOpenXrToggler`. If the user is on a system where OpenXR points to Monado or a custom runtime, OpenXR works, but the SteamVR-specific interaction profile paths (`OpenXrControllerProfileBootstrap.ConfigureSteamVrControllerProfiles` and `OpenXRInteractionProfilePatches.EnsureControllerProfiles` injecting `OculusTouchControllerProfile`) may not bind to the right device.
- **VR risk:** Controllers not paired; in-game recenter button unreachable.
- **Fix:** Read `OpenXRRuntime.name` after `Initialize`; if it doesn't contain "SteamVR" / "Oculus" / "Windows Mixed Reality" / "Monado", log a warning and skip the SteamVR-only profiles. Expose a config option to force profile selection.
- **Effort:** M

### [VR-MED-7] `EnableExperimentalSteamVrControllerProfiles` flag is set-and-forget

- **File:** `NOVR/VrTogglers/XrPluginOpenXrToggler.cs:11-25` and `NOVR/OpenXrControllerProfileBootstrap.cs:31-71`
- **Issue:** If the user toggles the flag at runtime via the BepInEx config UI, the bootstrap does **not** re-run. SteamVR-only profiles get installed once, on `SetUp`.
- **VR risk:** User enables the flag in the config, restarts the game, sees controllers, restarts again to try a different runtime — now they have SteamVR-only profiles injected permanently until they manually clear `OpenXRSettings`.
- **Fix:** Move bootstrap into `Core.Start` (after `VrTogglerManager`); re-read the flag each session. Don't make the runtime state sticky on the OpenXRSettings side; clear injected profiles on `Disable`.
- **Effort:** S

## Downgraded / removed findings (with reasons)

- ~~**[VR-CRITICAL-2] VrControllerInput filters the HMD pose path**~~ — **WRONG.** Re-read of `VrControllerInput.cs:60-128` confirms the OneEuro quaternion filter is allocated and applied only for `_rightRotFilter` / `_leftRotFilter`. The HMD path uses raw `_rawHeadPos` / `_rawHeadRot` (lines 244-256). No head smoothing. Finding removed.
- ~~**[VR-HIGH-1] Camera head-as-camera, parented to airframe**~~ — **REFRAMED.** The architecture (tracked camera parented to airframe root, local pose overwritten) is actually correct for the position channel and gives the right VR behavior for head-tracking. The bug is that the **HUD is world-fixed**, not the camera. Replaced with the more accurate description above.
- ~~**[VR-MED-7] `CalibrationAxes.All` includes pitch**~~ — **WRONG.** `CalibrateRotation` defaults to `CalibrationAxes.Yaw` (`NOVRHeadsetData.cs:36`), not `All`. The only pitch recenter that happens by default is via `CalibrateTranslation` defaulting to `All` (line 24), which on translation axis does NOT tilt the horizon — only translation axes. So no pitch-horizon-tilt bug. Finding removed.

## XInput DLL — independent review (`Uuvr.XInput/main.cpp`)

- **Files:** `Uuvr.XInput/main.cpp:1-273`, `xinput.def`
- **Status:** Functional stub. Returns `ERROR_SUCCESS` always (user 0); ignores vibration; ignores actual controller packets. The three `XInputSet*State` exports are the *only* writing path.
- **Risk:** If NOVR's VR input layer is broken (VR-CRITICAL-1 / VR-MED-6), the player gets a fully-controlled gamepad reporting all-buttons-set. Gamepad dead-zones nullified. Could cause accidental fire on takeoff.
- **Recommendation:** Either (a) complete the keyboard→XInput mapping in `XInputGetState` (the 96-137 commented block is a viable draft) and remove the `XInputSet*State` injection path, or (b) bind the getters to the actual VR controller state read from `OpenXRInput` directly. Today the static state is shared across all callers; multi-user-index handling is `user 0 succeeds, anything else disconnects` — fine for single-player local sim, would break in future co-op.

## Appendix: Architecture snapshot

(For review reference; produced by exploration subagents and refined against direct re-reads.)

- `NOVR/` BepInEx plugin: 79 source files, ~15,376 LOC; entry `NOVRPlugin.cs` (constructor does `Harmony.CreateAndPatchAll` + `PatchLoader.Apply` + `Core.Create`); `Core` MonoBehaviour spawns `VrCameraManager`, `NOVRHeadsetData`, `NOUIManager`, `VrTogglerManager` in `Start`. `VrCameraManager` hijacks `Main Camera` / `Menu Camera` GameObjects by parenting a NOVR `VrCamera` clone to each, then applying `NOVRPoseDriver` (raw HMD pose) every frame in `Update`/`LateUpdate`/`OnBeforeRender`. `NOVRHeadsetData` reads HMD via `InputDevices` + adds calibration offset. `NOUIManager` adds world-space UI camera rig with depth 100, copies URP camera stack from main. `VrTogglerManager` hard-codes `XrPluginOpenXrToggler` (the legacy `LegacyOpenVrToggler.cs` is dead).
- `NOVR.XR.OpenXR/`: ~110+ files, ~25k LOC. `OpenXRLoader` does `LoadOpenXRSymbols` → `Internal_InitializeSession` → `CreateSubsystems` → `RegisterOpenXRCallbacks`. 17 controller profiles; `OpenXRRestarter` handles `XrRestartRequested`, `XrLossPending`, etc.
- `NOVR.XR.OpenVR/`: 5 files, ~8.5k LOC. `OpenVRLoader` is `XRLoaderHelper`-derived, calls native `XRSDKOpenVR.dll`. Bundled only; never instantiated.
- `NOVR.XR.Management/`: 7 files, ~1,440 LOC. Replaces Unity's XR Management SDK; `XRGeneralSettings` has hard-coded `automaticLoading = false` (line 173-174) so NOVR's loader is the only one driven.
- `NOVR.Patcher/`: Mono.Cecil-driven rewrite of `Unity.XR.OpenXR.dll` to enforce `MultiPass` stereo + `Haptic` input layout. Does *not* touch `globalgamemanagers` (that code is dead). Drops OpenXR + native plugins into `NuclearOption_Data/Plugins/` per force.
- `NOVR.Installer/`: Avalonia 11.2.6, ~3.4k LOC. UI built in C# (no `.axaml`). Detects game via env+hardcoded paths, downloads BepInEx + NOVR from GitHub, writes `version.txt`. No SFX concatenation currently emitted.
- `NOVR.Build/`: MSBuild orchestrator. `BuildProjectReferencesBeforeResolveReferences` runs project refs first; `StageGameLayout` filters out `Unity.XR.*.dll`; `DeployToGame` copies to BepInEx dir; `CreateReleaseZip` produces `dist/NOVR.zip`.
- `Uuvr.XInput/`: C++ proxy for `xinput1_3.dll`. Returns fake state; exposes `XInputSet*State` helpers for NOVR to inject gamepad data.

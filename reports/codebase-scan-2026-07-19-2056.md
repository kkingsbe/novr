# NOVR Performance Optimization Report

**Scope:** GPU + CPU bottlenecks in the NOVR (Nuclear Option VR) BepInEx mod.
**Date:** 2026-07-19
**Skill used:** codebase-scan (focused on performance category)
**Working tree:** `C:\Users\Kyle\Documents\code\novr`

VR mod performance is uniquely constrained: every Unity `Update` already runs twice (per-eye) on most runtimes, plus a fixed `XRSettings.eyeTextureResolutionScale` target that the GPU must hit at 90 Hz. Every microsecond of CPU work and every extra draw call is multiplied. This report lists the highest-leverage optimizations first.

## Detailed Findings

### [PERF-001] `VrCanvasHitTester` does redundant raycasts against every registered canvas

- **File:** `NOVR/VrUi/VrCanvasHitTester.cs:243-323` (`RaycastCanvasPlanes`)
- **Also:** `NOVR/VrUi/VrUiCursor.cs:604, 645` (callers)
- **Issue:** For each registered canvas, the cursor calls `GraphicRaycaster.Raycast` (`VrCanvasHitTester.cs:351`) which walks the entire uGUI graphic tree under the canvas. With 5–10 canvases registered (HUD, recenter widget, native menu, mission picker, settings, etc.) this is O(canvas_count × graphic_count) per frame, plus the initial O(canvas_count) loop to find candidate planes.
- **Impact:** In a cockpit scene, the cursor update alone can do thousands of uGUI `Raycast` traversals per second — all for the common case where the cursor is parked off-screen and there is no active interaction. This is a per-frame, per-eye hot spot.
- **Recommendation:**
  - Cache a per-canvas, per-pointer spatial hash (or `RectTransform` AABB) and skip canvases whose rect doesn't overlap the ray.
  - Skip the raycast entirely when the cursor hasn't moved (use `_lastCursorTargetPos` delta > threshold) AND no trigger/click is active.
  - Consider replacing `RaycastCanvasPlanes` with a single sorted list of AABB hits followed by *one* `GraphicRaycaster.Raycast` on the chosen canvas.
  - Cap candidate count (e.g., stop at the first 3) since only the closest interactive hit matters.
- **Effort:** M

### [PERF-002] `EnforceClippedCameraStackPosition` is duplicated and fires too often

- **File:** `NOVR/VrUi/NOUIManager.cs:176-191, 203-239`
- **Issue:**
  - `EnforceClippedCameraStackPosition` mutates the URP `cameraStack` (a list) via `RemoveAt`/`Insert`.
  - It is called from `ConfigureUiCameras`, from `OnMainCameraChanged`, from `Update` (line 92-95 is a no-op `UpdateSmoothedPosition`; the enforcement actually runs from `ConfigureUiCameras` and from `OnMainCameraChanged`), but the safety coroutine (`EnforceStackAfterChange`) polls every 0.25 s for 2 seconds.
  - Even when the stack is already correct, the linear `IndexOf` + loop runs every poll cycle.
- **Impact:** URP's camera stack management is not free — it triggers pipeline rebuilds. Doing this 8 times per second when nothing has changed wastes a few microseconds and may invalidate cached camera state.
- **Recommendation:**
  - Early-out when `_cachedStackHash == currentHash`.
  - Replace the 0.25 s polling coroutine with a single-shot re-check 1 frame after `OnMainCameraChanged` (use `yield return null;` once).
  - Compute a hash (`HashCode.Combine(cameraStack.Count, ...) or a simple XOR over stable fields) instead of full `IndexOf` walk.
- **Effort:** S

### [PERF-003] Many UI behaviours rewrite `transform.position/rotation` to a constant value every frame

- **Files:**
  - `NOVR/VrUi/Components/NOVRGameplayUIBehaviour.cs:8-12` — sets `localScale = (0.003, 0.003, 0.003)` and `position = (0, 0, 3)` *every frame*
  - `NOVR/VrUi/Components/NOVRFlightHudBehavior.cs:35-39` — sets `position = (0,0,1050)`, `rotation = identity` every frame
  - `NOVR/VrUi/Components/NoVrHudBehavior.cs:7-11` — same pattern, every frame
  - `NOVR/VrUi/Components/NOVRStatusDisplayBehavior.cs:7-10` — sets position to constant `(630,145,1000)` every frame
  - `NOVR/VrUi/Components/NOVRTargetDesignatorBehavior.cs:9-15` — sets rotation/position based on `uiCam`, every frame
  - `NOVR/VrUi/Components/PositionZeroBehavior.cs:7-10` — sets position to `Vector3.zero` every frame (this is literally `transform.position = default;` on every frame, even when it's already zero)
- **Issue:** Each `transform.position = …` write marks the transform hierarchy dirty. For a HUD canvas with hundreds of `RectTransform` children, Unity then has to re-run the layout system + build the geometry. Doing this *every frame* even when nothing has changed is a known Unity performance anti-pattern.
- **Impact:** Major. This is one of the most common sources of "frame stutter" in VR — every dirty transform cascades through the UI rebuild, then the canvas mesh gets re-uploaded to the GPU. In stereo rendering, that's a double upload.
- **Recommendation:**
  - Move constant assignments to `Awake`/`Start` (or only when the parent changes).
  - For dynamic `PositionZeroBehavior`, gate on `if (transform.position != Vector3.zero) transform.position = Vector3.zero;`
  - For `NOVRTargetDesignatorBehavior` (which legitimately tracks the camera), gate on a delta threshold to skip writes when the camera hasn't moved > epsilon.
  - Better: replace these per-frame `Update` overrides with a single `LateUpdate` on `NOVRPoseDriver` that updates one transform, and parent the relevant UI elements to that transform so they move together.
- **Effort:** S

### [PERF-004] `Camera.main` is hit on the hot path via `APIBus`

- **File:** `NOVR/APIBus.cs:36-40`
- **Issue:** `APIBus.Update` runs `Camera.main` once per frame to detect main-camera changes. In Unity 2021+ URP, `Camera.main` does a tag scan if it isn't cached — it's typically O(scene_root_count) in the worst case. The code already caches this per-frame, so it's not as bad as it could be, but it runs *every frame* even when nothing changed.
- **Impact:** Small per-frame CPU, but the `OnMainCameraChanged` callback then does `GetComponent<UniversalAdditionalCameraData>()` on the new camera — which is fine on a transition but fires repeatedly if cameras swap mid-frame.
- **Recommendation:**
  - Use `Camera.onPostRender` / `RenderPipelineManager.beginContextRendering` to detect camera changes only when actually rendering, not every `Update`.
  - Or subscribe to `Camera.onSetCamera` (no-op overhead). Simplest: gate the `Camera.main` call on a 1-frame skip after the previous successful check, since main cameras change only on scene load.
- **Effort:** S

### [PERF-005] Per-frame string interpolation in verbose diagnostic paths

- **File:** `NOVR/VrUi/VrControllerInput.cs:135-145` and similar in `VrUiCursor.cs:242-255`
- **Issue:** The diagnostic branch builds a multi-value interpolated string every second. While it's throttled to 1 Hz and gated behind `VerboseDiagnostics.Value`, the *evaluation* of the gate (and the read of `Camera.main` for `camParent` in `VrControllerInput.cs:141`) runs every frame to check the throttle.
- **Impact:** Trivial CPU unless verbose diagnostics are on; but `Camera.main` is called every frame in this branch even when throttled out, because it's evaluated inside the gated block (so this is fine — it does not run when gate is false). **Reclassified: Low severity**, but the throttle check itself should be hoisted out of the per-frame hot path.
- **Recommendation:** Move the `VerboseDiagnostics.Value` read into a cached field updated via `ModConfiguration.Instance.Config.SettingChanged` event.
- **Effort:** S

### [PERF-006] `VrCameraManager.ScanForCameras` allocates a fresh camera array on every scene change

- **File:** `NOVR/VrCamera/VrCameraManager.cs:43-89`
- **Issue:** Every scene change triggers `Camera.allCamerasCount` + `Camera.GetAllCameras(cameras)` (allocates a new array), then walks all cameras calling `gameObject.AddComponent<VrCamera>()` or `StereoCamera`. The `_sceneDirty` flag prevents this from running every frame — that's good — but when it runs it touches every camera in the scene.
- **Impact:** Minor CPU spike on scene transitions; not per-frame. AddComponent allocates GC pressure.
- **Recommendation:** Use `Camera.allCameras` (no separate `allCamerasCount` call) into a reused cached array; reuse a single `List<Camera>` instead of allocating a fresh `Camera[]`.
- **Effort:** S

### [PERF-007] `VrUiCursor` always runs the full filter+raycast pipeline, even when no UI is active

- **File:** `NOVR/VrUi/VrUiCursor.cs:191-311`
- **Issue:** `Update()` runs the full pipeline (mode toggle polling, input read, controller filter, hit-test, click forwarding) every frame regardless of scene. When `_hasActiveCanvas == false`, the early-return path skips cursor positioning but still reads controller pose and trigger state.
- **Impact:** Modest CPU. The biggest fixed cost is the per-frame `VrControllerInput.TryGetDominantHand` call which triggers `EnsureFrame()` → OneEuroQuaternionFilter work for both hands even in menus where nothing moves.
- **Recommendation:** Early-out `VrControllerInput.EnsureFrame` for frames where no consumer has called it yet this frame (already does — good) and reduce `VrUiCursor.Update` work when `!Application.isFocused` (already done) and `!_cursor.activeSelf` and no deferred actions queued.
- **Effort:** S

### [PERF-008] `NativeVrUiRoot.Update` performs four deep `GetComponentsInChildren` walks per frame

- **File:** `NOVR/VrUi/Native/NativeVrUiRoot.cs:716-778` (`IsMissionPickerAvailable`, `IsMultiplayerMenuAvailable`, `IsSettingsMenuAvailable`, `IsWorkshopMenuAvailable`)
- **Issue:** Each of these methods does `GetComponentsInChildren<T>(true)` — a deep recursive walk — every frame the menu is open. With a main menu full of nested UI, this is hundreds of components per walk × 4 walks = thousands of component reads per frame, all on the main thread.
- **Impact:** Medium. The menu is the most UI-heavy screen, so this matters most there. It's also throttled by `MainMenuScanIntervalSeconds = 0.5f` for the *scan* but the per-frame `IsXxxAvailable` calls are not throttled.
- **Recommendation:**
  - Cache the result of each `IsXxxAvailable` query and refresh on scene load + game-state change (the existing `OnGameStateChanged` hook).
  - Or store a single `int _availableMenusMask` updated once per `sceneLoaded` and re-read it.
- **Effort:** M

### [PERF-009] Redundant `EnsureNativeMenuEnvironmentAssetCache` call in `Core.Update`

- **File:** `NOVR/Core.cs:96-105`
- **Issue:** `Update` runs `EnsureNativeMenuEnvironmentAssetCache()` every frame. That method (`Core.cs:107-116`) only does anything if the component is missing — which is set up in `Start` and only relevant right at startup. After the first frame, the if-branches always early-return.
- **Impact:** Trivial. Still — a per-frame null-check + `gameObject.GetComponent` call is wasteful.
- **Recommendation:** Remove the call from `Update`; the install in `Start`/`Awake` is sufficient.
- **Effort:** S

### [PERF-010] `NOVRBehaviour` base class subscribes every instance to `Application.onBeforeRender` + URP frame events

- **File:** `NOVR/NOVRBehaviour.cs:34-81`
- **Issue:** Every `NOVRBehaviour` (and there are dozens in `VrUi/Components` + the cockpit HUD) subscribes to `Application.onBeforeRender`, `RenderPipelineManager.beginFrameRendering`, and `RenderPipelineManager.endFrameRendering` events. Each subscription is a managed-delegate allocation and contributes to the per-frame invocation list. Most instances do nothing in their overrides — `OnBeforeRender` is virtual no-op for them.
- **Impact:** With ~30 NOVRBehaviour instances per scene, this is 30 managed delegates per event per frame. Unity's invocation cost is small per delegate but multiplied.
- **Recommendation:**
  - Move pose-driver `OnBeforeRender` to a single instance (`NOVRPoseDriver`) and let other components derive their pose from it (via parent transform).
  - Replace the base-class auto-subscription with explicit `protected override void OnEnable()` calls only in classes that need it.
- **Effort:** M

### [PERF-011] `PitchCompassBehavior` rotates 36+ slice transforms every frame instead of one parent

- **File:** `NOVR/VrUi/Components/PitchCompassBehavior.cs:38-57`
- **Issue:** The `_sliceRoot` transform is rotated every frame to match the cockpit inverse, and each of 36 slice children has `transform.position` baked in via `slice.transform.forward * 1000 + …` at build time (fine). But the parent rotation rebuild propagates through 36 child transforms each frame, which forces Unity to mark all 36 hierarchies dirty.
- **Impact:** 36 transform-dirty events per frame in flight → UI rebuild.
- **Recommendation:** Since the slices are fixed-offset quads on a sphere centered at the player, drive them with a custom shader uniform (`_CockpitRotation`) instead of mutating transforms. Or pre-compute the offset positions in shader space and just update one `Matrix4x4` uniform per frame.
- **Effort:** M

---

### [PERF-012] `OneEuroFilter` recomputes the same smoothing factor every axis every frame

- **File:** `NOVR/VrUi/OneEuroFilter.cs:38-44, 110-129`
- **Issue:** `SmoothingFactor(dt, cutoff)` computes `2π * cutoff * dt / (2π * cutoff * dt + 1)` per axis per frame. The `_dcCutoff` value never changes, so `ad` is constant for a given dt.
- **Impact:** Trivial CPU.
- **Recommendation:** Cache `_dcSmoothingFactor` per-frame in a `_lastDt` guard.
- **Effort:** S

### [PERF-013] `TurretVrCameraPatch` does 6 `FieldRef` reads per FixedUpdate per turret

- **File:** `NOVR/VrCamera/TurretVrCameraPatch.cs:18-65`
- **Issue:** The prefix reads six fields via `AccessTools.FieldRefAccess`. Each is a fast `Unsafe.As`-style ref read in Mono, slower in IL2CPP. Plus `AccessTools.MethodDelegate` per turret per fixed update.
- **Impact:** Low per call, but fires for every turret on the map. With ~4-8 turrets × 50 Hz fixed update = 200-400 reflective reads per second.
- **Recommendation:** Once the game's `Turret` class is identified, generate an `Il2CppInterop`-generated adapter (similar to NOVR's MCP bridge pattern) and cache it. Or use `[HarmonyPatch(typeof(Turret), "FixedUpdate")] [HarmonyPrefix]` and access fields via `__instance` (cached) + `Traverse` once per call.
- **Effort:** M

### [PERF-014] `VrCamera.Update` recomputes `HighestDepthVrCamera` every frame for every camera

- **File:** `NOVR/VrCamera/VrCamera.cs:31-37`
- **Issue:** Every `VrCamera` checks `if (HighestDepthVrCamera == null || ParentCamera.depth > HighestDepthVrCamera.CameraInUse.depth)` per frame. Since `CameraInUse` is just a getter that returns `ParentCamera`, this is a `Camera.depth` comparison. Cheap, but multiplied by every VR camera in scene (cockpit + selection + turret).
- **Impact:** Low.
- **Recommendation:** Update `HighestDepthVrCamera` only on `OnEnable`/`OnDisable` and on `Camera.depth` change (no such callback exists, so use a property setter or compute once after `VrCameraManager.ScanForCameras` completes).
- **Effort:** S

### [PERF-015] `NativeMenuEnvironmentAssetCache` uses `Resources.FindObjectsOfTypeAll` on a 0.5 s timer

- **File:** `NOVR/VrUi/Native/NativeMenuEnvironmentAssetCache.cs:529-549, 776-792, 794-810`
- **Issue:** `Resources.FindObjectsOfTypeAll` walks the entire object table (every loaded asset including inactive ones) and returns an array. This is one of Unity's most expensive APIs. The cache wraps calls in a 0.5 s throttle + a verbose-only gate, but `TryCacheFromLiveObjects` is still called on every 0.5 s tick (no gate).
- **Impact:** Medium spike on the main thread every 0.5 s while menu is open. With several asset types to find, this is multiple sweeps.
- **Recommendation:**
  - Once assets are cached, gate `Update` early-out on `if (_menuWarmupComplete && HasCloudPlane && HasWaterMaterial && CachedWeatherSetCount > 0) return;` to skip the entire poll loop after warmup completes.
  - Replace `FindObjectsOfTypeAll<T>` with cached references assigned when scenes load (use `SceneManager.sceneLoaded` + scene root walk, like `FindSceneComponent` already does).
- **Effort:** M

## Cross-cutting Recommendations

1. **Stop using `MonoBehaviour.Update` for static-value assignments.** This is the single biggest CPU saving available with almost no risk. Items 3, 9, 14 all collapse into the same fix.

2. **Consolidate per-frame pose updates.** Right now `NOVRPoseDriver`, `MainCameraSlaved`, `NOVRHMDBehavior`, `NOVRTargetDesignatorBehavior`, `NOUIManager.UpdateSmoothedPosition` all read the headset pose every frame from different code paths. A single `NOVRPoseDriver` instance writing to one parent transform (with other UI parented under it) would replace 5+ per-frame transforms with 1.

3. **Audit `Camera.main` and `Camera.allCameras` usage.** Both are O(scene) in URP. The codebase already caches one but not the other (`VrCameraManager.ScanForCameras`).

4. **Replace `FindObjectsOfTypeAll`/`GetComponentsInChildren<T>(true)` in Update paths** with event-driven scene-load hooks (already used in `UIBehaviorPatcher.cs`).

5. **For VR specifically:** the per-eye render means every Unity CPU call that runs in `Update` runs twice the work for the GPU (transform dirty → 2× UI mesh uploads). The optimizations above compound accordingly.

---

## Recommended Implementation Order (Highest ROI First)

1. **[PERF-003]** Move constant `transform.position`/`transform.rotation` writes out of `Update` into `Awake`/`Start` (or gate on delta). — 5 minutes per file, ~5 files. Should reduce VR UI mesh upload cost noticeably in flight.
2. **[PERF-002]** Replace camera-stack enforcement polling with a one-shot post-frame check. — 15 minutes.
3. **[PERF-015]** Early-out `NativeMenuEnvironmentAssetCache.Update` after warmup completes. — 10 minutes.
4. **[PERF-008]** Cache `IsXxxMenuAvailable` results and refresh on scene-load + game-state-change only. — 30 minutes.
5. **[PERF-001]** Replace `VrCanvasHitTester.RaycastCanvasPlanes`'s per-canvas `GraphicRaycaster.Raycast` with a per-canvas AABB pre-filter + single raycast on the chosen canvas. — 1-2 hours.
6. **[PERF-011]** Drive `PitchCompassBehavior` slices with a shader uniform instead of parent transform rotation. — 1-2 hours.
7. **[PERF-010]** Move per-instance `Application.onBeforeRender` subscriptions into the one component that needs them (`NOVRPoseDriver`). — 30 minutes.
8. **[PERF-013]** Cache turret field reads via generated IL2CPP adapter. — half a day, only if profiling shows it matters.

## Notes / Caveats

- No profiling data (Unity Profiler / RenderDoc / `FrameTimingManager`) is attached — these are static-analysis findings ranked by *expected* impact based on patterns. The first three (PERF-003, PERF-002, PERF-015) are essentially free wins and should be implemented first; only then profile to confirm PERF-001 / PERF-008 are the next bottlenecks.
- Several optimizations rely on assumptions about Unity 2021+ URP behavior (e.g., `Camera.main` cost, `cameraStack.RemoveAt` triggering pipeline rebuild). If the game runs on Unity 2019 or HDRP, some recommendations need adjustment.
- The mod is multi-target (`#if CPP` / `#if MODERN` guards). Performance-sensitive code should be re-verified in both Mono and IL2CPP builds after changes.
